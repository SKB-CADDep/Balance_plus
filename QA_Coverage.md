## 🔥 Часть 2. Нагрузочное тестирование (Locust)

Для проверки того, как система ведет себя при одновременной работе десятков инженеров, мы используем фреймворк[Locust](https://locust.io/). Он генерирует виртуальных пользователей (ботов), которые забрасывают API запросами по заданному сценарию.

### 🛠️ 2.1 Установка и подготовка

Нагрузочные тесты лежат в директории `tests/load/`.
Для локального запуска вам потребуется установить Locust в виртуальное окружение:

```bash
# Перейдите в корень проекта
pip install locust
```

> **Важно:** Перед запуском нагрузки убедитесь, что целевой микросервис (например, `valve-stems`) запущен в Docker или локально через `uvicorn`.

### 🚀 2.2 Как запустить тест (Пошагово)

1. Откройте терминал в корне проекта `Balance_plus`.
2. Запустите Locust, указав путь к файлу сценария:
   ```bash
   locust -f tests/load/locustfile.py
   ```
3. В терминале появится сообщение: `Starting web interface at http://0.0.0.0:8089`.
4. Откройте браузер и перейдите по адресу: **http://localhost:8089**

### ⚙️ 2.3 Настройки Web UI Locust

В браузере вы увидите стартовое окно. Вот что означают параметры, которые нужно ввести:

* **Number of users (Количество пользователей):** Пиковое число одновременных инженеров. Начните с `10` и постепенно увеличивайте до `50` или `100`.
* **Spawn rate (Скорость входа):** Сколько новых пользователей добавлять каждую секунду. Укажите `2` (система будет плавно наращивать нагрузку, добавляя по 2 пользователя в сек., пока не достигнет пика).
* **Host (Целевой сервер):** Базовый URL микросервиса, который мы "бьем". 
  * Для Калькулятора штоков (Valve Stems): `http://localhost:5253`
  * Для Оркестратора: `http://localhost:8005`

Нажмите **"Start swarming"** для начала атаки.

### 🧠 2.4 Как устроен наш сценарий (Разбор кода)

Скрипт `tests/load/locustfile.py` не просто "спамит" один эндпоинт, он имитирует **реальное поведение человека**.

1. **Паузы (Wait time):** `wait_time = between(1, 5)` означает, что после каждого действия виртуальный инженер "думает" от 1 до 5 секунд перед следующим кликом.
2. **Вес задач (Tasks):** 
   * `@task(3) calculate_stems`: Расчет физики (тяжелая операция) запускается с шансом 3/5.
   * `@task(1) list_turbines`: Запрос справочника турбин из БД (легкая операция) — шанс 1/5.
   * `@task(1) health_check`: Пинг сервера — шанс 1/5.
3. **Рандомизация данных:** В сценарии расчета мы случайно меняем температуру пара (`T_fresh = random.uniform(540, 560)`). Это сделано специально, чтобы СУБД или сервер не могли отдать закешированный ответ. Физический движок будет вынужден честно считать математику каждый раз.

### 📈 2.5 Как анализировать результаты

В интерфейсе Locust перейдите на вкладку **Charts**. На что смотреть:

1. **RPS (Requests per Second):** Общая пропускная способность. Если RPS перестал расти при добавлении новых пользователей — сервер уперся в потолок своих возможностей.
2. **Response Times (Время ответа):** 
   * Смотрите на **95th percentile**. Это время, за которое обслуживаются 95% пользователей.
   * Если график ползет вверх (переваливает за 1-2 секунды) — физический движок (CPU-bound задача) блокирует Event Loop FastAPI. *Решение: в будущем выносить расчеты в Celery (фоновые воркеры).*
3. **Failures (Ошибки):** Если на графике появляются красные линии, перейдите на вкладку **Failures**:
   * **HTTP 500:** Скорее всего, база данных (PostgreSQL) исчерпала пул подключений (Connection Pool).
   * **HTTP 422:** Ошибка валидации (Locust сгенерировал кривой JSON).
   * **Timeout:** Сервер так сильно завис, что сбросил соединение.

### 🛑 2.6 Рекомендации по итогам QA
* **Среда тестирования:** Не проводите серьезные нагрузочные тесты (более 200 пользователей) на `localhost`, если база данных, приложение и сам Locust запущены на одной машине. Они будут конкурировать за CPU, искажая результаты.
* **БД:** При увеличении RPS следите за логами контейнера базы данных (`docker logs balance_db`), чтобы вовремя заметить ошибки нехватки памяти (OOM) или блокировки таблиц.
