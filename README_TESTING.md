# 🚀 Руководство по Универсальному Тест-Раннеру (Balance+)

Данный инструмент объединяет тестирование всех слоев монорепозитория (БД, API, физические движки и сложную логику) в единый удобный консольный интерфейс. 
Система поддерживает **4 типа тестов**, позволяя писать их как разработчикам на Python, так и аналитикам на чистом YAML без знаний программирования.

---

## 📁 1. Как добавить новую группу тестов?

Чтобы папка с вашими тестами появилась в главном меню Оркестратора, в ней **обязательно** должен лежать файл `__group__.yml`. Без него сканер проигнорирует директорию.

Создайте файл `__group__.yml` в нужной папке и заполните его:
```yaml
name: "Название вашей группы (до 25 символов)"
description: "Подробное описание того, что именно тут тестируется"
```

## 🐍 2. Классические Python-тесты (Файлы `test_*.py`)

**Для чего:** Сложные юнит-тесты, работа с моками (`MagicMock`), асинхронные проверки логики.
**Исполнитель:** Стандартный `pytest`.

⚠️ **ВАЖНОЕ ПРАВИЛО ОФОРМЛЕНИЯ:**
Чтобы Оркестратор красиво отобразил описание вашего файла в меню, **обязательно пишите описание в тройных кавычках `"""` в самой первой строке файла!** Обычные комментарии через `#` сканер меню не увидит.

**Пример `test_logic.py`:**
```python
"""
Тестирование сложной бизнес-логики с использованием моков
"""
import pytest
from unittest.mock import MagicMock

class TestBusinessLogic:
    def test_something(self):
        assert 1 == 1
```

## 🌐 3. Интеграционные API-тесты (Файлы `test_*.tavern.yaml`)

**Для чего:** Проверка HTTP-запросов (REST API) как "черного ящика". Идеально для тестировщиков.
**Исполнитель:** Плагин `Tavern` (запросы уходят на реальный сервер).

**Пример `test_calculations.tavern.yaml`:**
```yaml
test_name: "Сохранение результатов расчетов (API)"

stages:
  - name: "Проверка ошибки 400 при неверном ID"
    request:
      url: "http://localhost:5253/api/v1/calculations/save"
      method: POST
      json:
        task_iid: 99999
    response:
      status_code: 400
```
*Примечание: `test_name` автоматически подтянется как описание файла в CLI-меню.*

## 🗄️ 4. Тесты Базы Данных (Файлы `test_*.db.yaml`)

**Для чего:** Проверка сложных SQL-запросов и CRUD-операций.
**Исполнитель:** Кастомный плагин `conftest.py` (Pydantic + SQLAlchemy). 
**Особенность:** После выполнения каждого теста автоматически делается `ROLLBACK` (откат транзакции), поэтому ваша база всегда остается чистой!

**Пример `test_turbines.db.yaml`:**
```yaml
description: "Проверка операций с таблицей турбин"

tests:
  - id: "insert_and_check"
    description: "Добавление турбины и проверка ее параметров"
    query: >
      INSERT INTO turbines (name, power) 
      VALUES (:name, :power) 
      RETURNING name, power;
    params:
      name: "K-200"
      power: 200
    expected_rows:
      - name: "K-200"
        power: 200
```

## 🧮 5. Математические расчеты и Стратегии (Файлы `test_*_calc.py`)

**Для чего:** Сверка огромных массивов данных (JSON) с результатами работы физических движков (Берман, Метро-Виккерс, Штоки).
**Исполнитель:** Кастомный плагин `conftest.py`. Автоматически сравнивает `float` числа с учетом погрешности процессора.

⚠️ **ПРАВИЛО ОПИСАНИЯ:** Как и в обычных Python-тестах, используйте `""" ... """` вверху файла.

**Пример `test_vku_calc.py`:**
```python
"""
Валидация математики: Расчет ВКУ по эталонным JSON
"""
from app.domain.physics import vku_calculate

# Обязательная переменная: какую функцию тестируем
target_function = vku_calculate

# Массив с данными (можно генерировать динамически, читая JSON-файлы с диска)
tests =[
    {
        "id": "vku_mode_1",
        "input": {"pressure": 4.5, "flow": 500},
        "expected": {"efficiency": 0.85, "power": 100.5}
    }
]
```

## 🎮 6. Как запускать тесты и сохранять логи?

Тесты всегда запускаются через единую точку входа — скрипт Оркестратора.

**Запуск:**
Откройте терминал в активированном виртуальном окружении проекта (или внутри Docker-контейнера) и выполните:
```bash
python test_runner.py
```

### 🐞 Отладка и Логирование (Тумблер `[ l ]`)
По умолчанию система **не сохраняет** логи упавших тестов, чтобы не засорять жесткий диск. 
Если ваш математический или API тест упал, и вы хотите посмотреть подробный отчет с цифрами (что ожидалось, а что получилось):
1. Находясь в меню Оркестратора, нажмите клавишу `l` (английская L) и `Enter`.
2. Строка переключится в состояние: `Сохранять логи при ошибках: ВКЛ`.
3. Запустите падающий тест еще раз.
4. Зайдите в папку `logs/` (она создастся автоматически там, где был запущен pytest). В ней появится файл вида `log_test_vku_calc_20260312_104500.txt` с полным Traceback'ом ошибки.

## 🛠 7. Частые проблемы (Troubleshooting)

1. **`ModuleNotFoundError` при запуске юнит-тестов:** 
   * **Причина:** Скрипт запущен из глобального Питона Windows, а не из виртуального окружения (Poetry/venv), где установлены библиотеки (`WSAProperties`, `FastAPI`).
   * **Решение:** Выполните `poetry shell` перед запуском `python test_runner.py` или запускайте раннер внутри запущенного Docker-контейнера (`docker-compose exec backend python test_runner.py`).

2. **Ошибки `Connection refused` или `Timeout` при тестах БД/API:**
   * **Причина:** Тесты пытаются постучаться в базу данных или API, которые не запущены, либо порты не проброшены.
   * **Решение:** Проверьте `docker-compose.yml` (открыты ли порты `5432` / `5253`). При необходимости, жестко укажите `localhost` и правильный порт в начале вашего файла с тестом через `os.environ["POSTGRES_SERVER"] = "localhost"`.

3. **База данных пустая (ошибка `relation does not exist`):**
   * **Причина:** Docker игнорирует ваш `init.dump`, так как контейнер базы данных уже запускался ранее.
   * **Решение:** Выполните пересоздание тома: `docker-compose down -v`, а затем `docker-compose up -d`. При чистом старте база сама распакует дамп.
