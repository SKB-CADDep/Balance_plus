# Спецификация библиотеки «UniConv»

---

**Раздел 1. Общая информация**

| Поле | Значение |
|------|----------|
| Название библиотеки | UniConv (Unit Converter) |
| Назначение | Расширяемая библиотека конвертации единиц измерения с поддержкой UI-форматирования, пресетов единиц и инженерных таблиц |
| Язык реализации | Python 3.x |
| Соответствие стандартам | - |
| Версия спецификации | 1.2 |

---

**Раздел 2. Архитектура и Особенности**

> **Цель:**
> Объединить гибкость динамического добавления единиц с жёсткой инженерной логикой и полным набором данных реестра.
>
> **Ключевые особенности:**
> 1.  **Идентификация по ID:** Каждая величина однозначно определяется **строковым ID** (`"0"`, `"1"`, …, `"47"`). Все методы API принимают именно ID. Русские (`name_RU`) и английские (`name_ENG`) наименования используются **только для отображения** в UI и не участвуют в поиске.
> 2.  **Разделение Код/UI:** У каждой единицы есть ASCII-код для использования в коде/БД (напр. `м3/ч`) и UI-представление для вывода на экран (напр. `м³/ч`).
> 3.  **Табличные конвертации:** Поддержка нелинейных зависимостей (Твердость) через встроенные таблицы данных.
> 4.  **Расширенная термодинамика:** Поддержка температурных шкал C, K, F и Re (Реомюр).
> 5.  **Пресеты единиц:** Именованные наборы единиц отображения (СИ, Технические, Имперская и т.п.), хранящиеся отдельно от реестра величин и адресуемые по ID.
> 6.  ~**Внешние источники данных:** Реестр величин, таблица твёрдости и пресеты поставляются отдельными файлами (`units_registry.json`, `hardness_data.json`, `presets.json`) и подключаются при инициализации.~

---

**Раздел 3. Функциональные требования (API)**

**3.1. Основные методы класса `UnitConverter`**

> Во всех методах параметр `type_id: str` — это строковый ID величины из `units_registry.json` (например `"0"`, `"47"`). Русские/английские имена **не принимаются** API — при необходимости преобразование выполняется вызывающим кодом через `get_parameter_info`.

| Метод | Сигнатура | Описание |
|-------|-----------|----------|
| **convert** | `(val, from_u, to_u, type_id) -> Optional[float]` | Сквозная конвертация. Аргумент `type_id` — строковый ID величины. `from_u`/`to_u` — коды единиц (ключи `factors`). При невозможности конвертации возвращает `None`. |
| **get_available_units** | `(type_id) -> list[dict]` | Возвращает список словарей: `{'code': 'м3/ч', 'ui': 'м³/ч', 'name': 'Кубический метр в час'}`. |
| **get_parameter_info** | `(type_id) -> dict` | Возвращает метаданные параметра: `{'id': '47', 'name_RU': '...', 'name_ENG': '...', 'base_unit': '...'}`. Если ID не найден — `None`. |
| ~**add_unit**~ | ~`(...)`~ | ~Динамическое добавление пользовательских единиц к существующему `type_id`.~ |
| **list_presets** | `() -> list[str]` | Возвращает список имён именованных пресетов единиц измерения, доступных в библиотеке. |
| **get_preset** | `(name) -> dict` | Возвращает пресет по имени в виде словаря `type_id -> unit_code`. Если пресет не найден — возвращает `None`. |
| **apply_preset** | `(name) -> dict` | Возвращает «разрешённый» пресет: словарь `type_id -> {'code': ..., 'ui': ...}` с проверкой, что каждая единица существует в соответствующем `factors` реестра. Единицы, отсутствующие в реестре, отбрасываются, о чём пишется предупреждение в лог. |

**Раздел 4. Бизнес-правила (Логика)**

| ID | Правило | Формула / Логика |
|----|---------|-------------------|
| **BR-01** | **Линейная конвертация** | Для всех *линейных* величин коэффициент `Factor` задаётся **в сторону базовой единицы** (*to base*).<br>**Определение:** $Factor_u$ — коэффициент перевода из единицы $u$ в базовую единицу данного типа.<br>В формулах используются: $Factor_{from}$ (для `from_u`) и $Factor_{to}$ (для `to_u`).<br>**Приведение к базовой:** $$Val_{base} = Val_{in} \times Factor_{from}$$<br>**Переход из базовой в целевую:** $$Val_{out} = \frac{Val_{base}}{Factor_{to}}$$<br>**Итоговая формула:** $$Val_{out} = Val_{in} \times \frac{Factor_{from}}{Factor_{to}}$$<br>Для базовой единицы: $Factor_{base}=1.0$. |
| **BR-02** | **Температурные сдвиги** | Для величины с `id = "1"` (Температура) используется **аффинная конвертация** (со сдвигом), правило **BR-01 не применяется**.<br>**Базовая единица температуры:** `C`.<br>**Приведение к базовой (°C):**<br>**Кельвин (K):** $C = K - 273.15$<br>**Фаренгейт (F):** $C = (F - 32) \times 5/9$<br>**Реомюр (Re):** $C = 1.25 \times Re$<br>**Обратное преобразование из базовой (°C):**<br>**Кельвин (K):** $K = C + 273.15$<br>**Фаренгейт (F):** $F = C \times 9/5 + 32$<br>**Реомюр (Re):** $Re = 0.8 \times C$<br>**Алгоритм:** сначала перевести $Val_{in}$ в $C$, затем из $C$ — в целевую единицу. |
| **BR-03** | **Твердость: шкалы и табличная конвертация** | Величина `id = "34"` (Твёрдость) имеет **шкалы (единицы)** `d10`, `HB`, `HRA`, `HRC`, `HRB`, `HV`, `HSD` и использует таблицу `HARDNESS_DATA`; **BR-01 не применяется**.<br>**`None` = нет данных:** такие значения **игнорируются** в интерполяции.<br>**HB → S:** интерполяция по `HB` по строкам, где $S \neq \text{None}$.<br>**S → HB:** обратная интерполяция по $S$ по строкам, где $S \neq \text{None}$.<br>**A → B:** \(A \rightarrow HB \rightarrow B\)<br>**Границы:** вне диапазона/нет интервала (в т.ч. из-за `None`) → `None`; экстраполяция запрещена.<br>**Расчёт остальных шкал:** задана одна шкала → остальные пытаемся получить через `HB`, иначе для вывода ставим `-`. |
| **BR-04** | **Коды и UI** | При поиске единицы (`from_u`, `to_u`) поиск ведётся строго по полю **«Единица (код)»** (ключи в `factors`). Поле **«Единица (UI)»** (значения в `display_labels`) используется только для отображения во фронтенде/отчётах. |
| **BR-05** | **Пресеты единиц измерения** | Библиотека хранит **именованные пресеты единиц измерения** — наборы единиц отображения по умолчанию для величин из реестра.<br><br>**Формат:** словарь `presets[name] = {'name_RU': ..., 'name_ENG': ..., 'units': {type_id → unit_code}}`.<br><br>**Источник:** файл `presets.json`, подключаемый при инициализации.<br><br>**Связь с реестром:** ключ внутри `units` — это **ID величины** (строка) из `units_registry.json`; значение — **код единицы** (ключ из `factors` этой величины).<br><br>**Валидация:** при вызове `apply_preset(name)` библиотека проверяет, что для каждого `type_id` величина существует и указанный `unit_code` присутствует в её `factors`. Невалидные пары отбрасываются, факт отбрасывания логируется.<br><br>**Доступ:** `list_presets()` — перечень имён, `get_preset(name)` — «сырой» словарь `type_id → unit_code`, `apply_preset(name)` — валидированный словарь `type_id → {'code', 'ui'}`.<br><br>**Вне скоупа:** способ применения пресета в приложении (UI-кнопка, профиль пользователя, конфиг) — ответственность вызывающего кода. |
| **BR-06** | **Библиотека констант (запрет «магических чисел»)** | Все числовые константы, используемые в формулах и конвертациях (например `273.15`, `32`, `9/5`, `5/9`, а также $\pi$, $e$, стандартное $g$ и т.п.), должны храниться **в отдельном реестре/модуле констант** (например, `constants`).<br><br>**Требование:** в коде алгоритмов конвертации (методы `convert`, интерполяция, формулы температур и т.д.) **не должно быть «вшитых» чисел**; допускается использование только ссылок на константы из этого реестра.<br><br>**Дополнение:** каждая константа должна быть **именованной и документированной** (минимум: `id/ключ`, `значение`, `описание/назначение`; при наличии — `единица измерения` и `источник`).<br><br>**Примечание:** табличные справочники (например `HARDNESS_DATA`) хранятся отдельно от кода (в конфиге/данных) и подключаются как источник данных.<br><br>**Смотри приложение 4** |
| **BR-07** | **Идентификаторы величин** | Каждая величина в реестре имеет **уникальный строковый ID** (`"0"`, `"1"`, …, `"47"`). ID — это **единственный ключ доступа** к величине через публичное API; он же используется в пресетах и внешних маппингах. Русские и английские наименования (`name_RU`, `name_ENG`) носят справочный характер и **не используются для поиска**. Переименование величины — безопасно; смена ID — breaking change. |
| **BR-08** | **Стандартное ускорение свободного падения (`G_STANDARD`)** | Все коэффициенты `factors`, численно выведенные из стандартного ускорения свободного падения `g₀ = 9.80665 м/с²`, **должны выражаться через именованную константу `G_STANDARD`** из модуля `constants` (см. BR-06) и/или производные от неё составные константы.<br><br>**Запрещено:** прямое использование числа `9.80665` (а также любых его производных, например `0.0980665`, `9.80665e-3`, `4.44822`, `735.499`) вне модуля `constants`.<br><br>**Перечень величин, чьи `factors` обязаны ссылаться на `G_STANDARD` (прямо или через составные константы):**<br>— `0` Давление<br>— `17` Мощность<br>— `20` Сила<br>— `21` Момент силы<br>— `36` Предел ползучести<br>— `37` Предел прочности<br>— `38` Предел длительной прочности<br>— `39` Предел текучести<br>— `40` Предел выносливости<br>— `41` Модуль упругости<br>— `42` Ударная вязкость<br>— `46` Коэффициент пропорциональности<br><br>**Составные константы (вводятся в `constants` для избежания повторного вывода):**<br>— `KGF_TO_N = G_STANDARD`<br>— `LB_TO_KG = 0.45359237` (точно)<br>— `LBF_TO_N = LB_TO_KG · G_STANDARD`<br>— `HP_METRIC_TO_W = 75 · G_STANDARD`<br>— `ATM_TO_PA = 101325` (точно, без `g`)<br>— `MMHG_TO_PA = 133.322387415` (составная, через `ρ_Hg` и `g`)<br>— `RHO_H2O_4C = 1000` (кг/м³) — для `мм вод.ст.`<br><br>**Оговорки:**<br>1. `мм вод.ст.` формально не требует `G_STANDARD` (числитель и знаменатель содержат `g`, которое сокращается). Допускается оставить как `1e-4` со ссылкой на `RHO_H2O_4C`.<br>2. `мм рт.ст.` зависит от `g` и `ρ_Hg`. Вводится составная константа `MMHG_TO_PA`, разворачивать её на `g` и `ρ_Hg` в `factors` не требуется.<br>3. `кгс/м4` и `тс/м4` в `id = "46"` **не содержат `g`** — это чисто размерные отношения `см⁴ ↔ м⁴` и `кгс ↔ тс`. |

> **Примечание:** библиотека предоставляет атомарную операцию `convert(val, from_u, to_u, type_id)`; порядок и количество вызовов конвертации (например, приведение к базовым или к единицам методики) определяется вызывающим кодом приложения.

**Раздел 7. Пресеты единиц измерения**

Пресеты — это именованные наборы единиц отображения по умолчанию для каждой величины реестра. Хранятся отдельным файлом:

> **`presets.json`** — структура:
> ```json
> {
>   "presets": {
>     "<name>": {
>       "name_RU": "...",
>       "name_ENG": "...",
>       "units": { "<type_id>": "<unit_code>", ... }
>     }
>   }
> }
> ```

**Ключи в `units`** — строковые ID величин из `units_registry.json`. **Значения** — коды единиц (ключи из `factors` соответствующей величины).

**Пример (фрагмент):**

| Пресет | type_id `0` (Давление) | type_id `24` (Длина) | type_id `17` (Мощность) | type_id `47` (Угл. скорость) |
|:---|:---:|:---:|:---:|:---:|
| `SI`       | МПа | м  | кВт | рад/с |
| `TECH`     | кгс/см2 | мм | МВт | об/мин |
| `IMPERIAL` | psi | дюймы | л.с. | об/мин |

**Правила работы с пресетами:**

1.  Пресет — это **слой отображения**, он не меняет значения в хранилище. Значения в БД всегда лежат в базовых единицах реестра (`base_unit`).
2.  При отображении: `ui_value = convert(stored_value, base_unit, preset_unit, type_id)`, затем формат через `display_labels[preset_unit]`.
3.  При вводе от пользователя: `stored_value = convert(ui_value, preset_unit, base_unit, type_id)`.
4.  Библиотека **не применяет** пресеты автоматически — она лишь предоставляет их через `list_presets()`, `get_preset()`, `apply_preset()`. Момент применения определяет вызывающий код.
5.  При добавлении новой величины в реестр существующие пресеты можно не трогать — отсутствующие ID игнорируются при применении (`apply_preset` их просто пропустит). Это позволяет расширять реестр без синхронного обновления всех пресетов.
6.  При добавлении новой единицы в `factors` существующей величины все пресеты, ссылающиеся на неё, автоматически получают возможность её использовать — править `presets.json` не нужно.

**Раздел 8. Критерии приёмки (Definition of Done)**

Задача считается выполненной, если реализован класс `UnitConverter`, удовлетворяющий следующим требованиям:

1.  **Идентификация по ID:**
    *   Все публичные методы (`convert`, `get_available_units`, `get_parameter_info`, `add_unit`) принимают `type_id` — строковый ID величины.
    *   Русские/английские имена (`name_RU`, `name_ENG`) возвращаются только через `get_parameter_info` и **не используются** как ключ поиска.
    *   Попытка обратиться по неизвестному ID возвращает `None` (или вызывает документированное исключение) — единообразно для всех методов.

2.  ~**Источники данных:**~
    *   ~Реестр величин загружается из внешнего файла `units_registry.json`. Обеспечена корректная работа с UTF-8 (в текущей поставке файл имеет признаки повреждения кодировки — должен быть пересохранён в UTF-8).~
    *   ~Таблица твёрдости загружается из `hardness_data.json`; `None` трактуется как «нет данных».~
    *   ~Пресеты загружаются из `presets.json`; структура соответствует Разделу 7.~

3.  **Структура данных:**
    *   `get_available_units(type_id)` возвращает полную структуру для UI: код, UI-название.
    *   `get_parameter_info(type_id)` возвращает `{'id', 'name_RU', 'name_ENG', 'base_unit'}`.
    *   Все коэффициенты из `units_registry.json` используются «как есть», без дополнительного округления.

4.  **Логика конвертации:**
    *   Реализована сквозная конвертация `convert(val, from, to, type_id)`.
    *   Работает конвертация температуры (`type_id = "1"`): C ↔ K ↔ F ↔ Re (Реомюр).
    *   Работает интерполяция твёрдости (`type_id = "34"`):
        *   точное совпадение значения из таблицы;
        *   линейная интерполяция между точками;
        *   возврат `None` при выходе за границы диапазона таблицы или при невозможности интерполяции (экстраполяция запрещена).

5.  **Логика пресетов:**
    *   `list_presets()` возвращает список имён пресетов.
    *   `get_preset(name)` возвращает «сырой» словарь `type_id → unit_code`.
    *   `apply_preset(name)` возвращает валидированный словарь `type_id → {'code', 'ui'}`, отбрасывая несуществующие пары и логируя предупреждения.
    *   Для несуществующего пресета возвращается `None`.

6.  **Качество кода:**
    *   Код покрыт Unit-тестами (минимум 1 тест на каждую величину реестра + тесты на граничные условия твёрдости + тесты на пресеты).
    *   Отсутствуют «магические числа» в формулах (все коэффициенты вынесены в константы или конфиг).
    *   Погрешность обратной конвертации (`A → B → A`) не превышает `1e-5` (за исключением табличных значений твёрдости, где возможны потери точности интерполяции).

7.  **Артефакты:**
    *   Исходный код библиотеки (`.py`).
    *   Набор тестов (`tests/`).
    *   Файлы данных: `units_registry.json`, `hardness_data.json`, `presets.json`.
    *   Файл `README.md` с примерами использования (обращение по ID, Hardness, UI-units, работа с пресетами).

8.  **Константы и `G_STANDARD`:**
    *   Модуль `constants` содержит как минимум: `G_STANDARD`, `KGF_TO_N`, `LB_TO_KG`, `LBF_TO_N`, `HP_METRIC_TO_W`, `ATM_TO_PA`, `MMHG_TO_PA`, `RHO_H2O_4C`.
    *   В `factors` величин с ID `0, 17, 20, 21, 36, 37, 38, 39, 40, 41, 42, 46` отсутствуют литеральные вхождения `9.80665`, `0.0980665`, `9.80665e-3`, `4.44822`, `735.499` и их эквивалентов — все они выражены через `G_STANDARD` и/или составные константы из `constants`.
    *   Добавлен тест-«страж» (grep-тест), сканирующий файлы библиотеки и реестра на наличие запрещённых литералов вне модуля `constants`.
    *   Тест на обратимость конвертации (`A → B → A`) с точностью `1e-5` проходит для всех перечисленных выше величин, что косвенно подтверждает корректность выражений через `G_STANDARD`.

# BR-06 — Библиотека констант

## BR-06.1. Назначение и область действия

> Все числа, которые **не являются очевидными и общепонятными** (то есть всё, кроме `0`, `1`, `2`, `−1`, `0.5`, а также степеней десяти вида `10ⁿ`), должны быть вынесены в **отдельный модуль `constants`** и использоваться по имени.
>
> Каждая константа обязана иметь: **имя в UPPER_SNAKE_CASE**, **значение**, **единицу измерения**, **одну строку docstring-описания** и, где применимо, **ссылку на источник** (ГОСТ, ISO, SI Brochure и т.п.).
>
> **В коде конвертации и в файле `units_registry.json` — только ссылки на имена констант, никаких «магических» чисел.**

**Что именно вынести** — ниже полный перечень, разбитый по категориям. Если числа нет в этих таблицах — оно либо тривиально (`0`, `1`, `2`, `0.5`), либо степень десяти (`10³`, `10⁻⁶`), и его можно писать напрямую.

---

## BR-06.6. Составные (производные) константы

Эти константы получаются из комбинации BR-06.3 и BR-06.4. Вводить их **отдельно обязательно**, если они используются в `factors` больше одного раза: это исключает повторение формул и рассинхронизацию.

| Ключ | Формула | Значение (справочно) | Единица | Где используется |
|:---|:---|:---:|:---:|:---|
| `KGF_TO_N` | `G_STANDARD` | `9.80665` | Н | id 20, 21, 36–42, 46 |
| `LBF_TO_N` | `LB_TO_KG · G_STANDARD` | `4.4482216152605` | Н | id 0, 20, 42, 46 |
| `HP_METRIC_TO_W` | `75 · G_STANDARD` | `735.49875` | Вт | id 17 |
| `MMHG_TO_PA` | `133.322387415` | `133.322387415` | Па | id 0 |
| `MMH2O_TO_PA` | `RHO_H2O_4C · G_STANDARD / 1000` | `9.80665` | Па | id 0 |

```

```

## BR-06.7. Правила применения

1. **Импорт:** в алгоритмах конвертации допускается `from .constants import G_STANDARD, KGF_TO_N, ...` или `from . import constants as C` с обращением `C.G_STANDARD`.
2. **Запрещено** использовать числовые литералы, соответствующие значениям из таблиц BR-06.2–BR-06.6, где-либо вне модуля `constants`.
3. **Реестр `units_registry.json`** на этапе загрузки разворачивает ссылки на имена констант в числа **один раз при инициализации**, кэширует и далее работает только с числами. Формат ссылки в JSON: строка вида `"@G_STANDARD"`, `"@KGF_TO_N"` и т.п. (префикс `@` явно отделяет имя константы от значения единицы).
4. **Именование:** только `UPPER_SNAKE_CASE`. Суффикс `_TO_XXX` используется для конверсионных констант, суффикс `_OFFSET` — для сдвигов, `_RATIO` — для отношений.
5. **Обязательный тест-«страж»:** в CI запускается проверка, что в файлах библиотеки (кроме `constants.py`) и в `units_registry.json` (кроме секции `factors` после раскрытия) отсутствуют литералы `9.80665`, `0.45359237`, `273.15`, `101325`, `133.322387415`, `735.49875`, `4.44822`, `25.4` и т.п.

---

## BR-06.8. Что НЕ является константой (можно писать напрямую)

Программисты часто спрашивают, нужно ли выносить всё. **Нет.** Следующее выносить не нужно:

- `0`, `1`, `2`, `-1`, `0.5` — очевидные числа;
- степени десяти: `10³`, `10⁶`, `10⁻³`, `1e-6` — масштабные множители SI;
- строковые метки (`"table"`, `"offset_k"`, `"offset_f"`) — это не числа, а ключи алгоритмов, они живут в `constants` как строки и используются в реестре;
- размерные степени длины (`мм²`, `мм³`, `мм⁴`) — они задаются через `INCH_TO_MM` возведением в степень, а не вводятся как отдельные константы.
