# 🚀 Руководство по нагрузочному тестированию (Locust)

Данный фреймворк предназначен для получения **Baseline** (базовой линии) производительности синхронных эндпоинтов и обоснования перехода на асинхронные очереди (Celery).

## 📋 Подготовка
Перед запуском убедитесь, что у вас установлен Locust:
```bash
pip install locust
```

## 🏗 Структура тестов
Тесты разделены на 3 независимых сценария для каждого микросервиса:
1.  `locust_valves.py` — расчеты протечек в штоках (порт 5253).
2.  `locust_condensers.py` — теплофизические расчеты конденсаторов (порт 8010).
3.  `locust_orchestrator.py` — работа с задачами и GitLab API (порт 8005).

---

## 1. Калькулятор Штоков (Valve Stems)
**Цель:** Проверить нагрузку на `ValvePhysicsEngine` при итерационных расчетах.

*   **Команда запуска:**
    ```bash
    locust -f tests/load/locust_valves.py --host http://localhost:5253
    ```
*   **Сценарий:**
    *   75% трафика: POST-запросы на `/api/v1/calculate` (тяжелая математика).
    *   25% трафика: GET-запросы к БД турбин.
*   **Ожидаемый Baseline:** p95 должен быть в пределах 200–500мс. Если выше 800мс — система требует Celery.

---

## 2. Калькулятор Конденсаторов (Condenser Calculator)
**Цель:** Проверить сходимость метода Бермана при множественных одновременных запросах.

*   **Команда запуска:**
    ```bash
    locust -f tests/load/locust_condensers.py --host http://localhost:8010
    ```
*   **Сценарий:**
    *   Обстрел эндпоинта `/api/v1/calculate`. 
    *   Используются заглавные параметры `G_steam`, `W_main`, `T1_main` согласно схемам Pydantic.
    *   **Важно:** Скрипт автоматически подставляет `H_steam`, без которого метод Бермана выдаст ошибку 422.
*   **Ожидаемый Baseline:** Метод Бермана итерационный, поэтому при 50 юзерах ожидается значительный рост времени отклика.

---

## 3. Оркестратор (Balance Orchestrator)
**Цель:** Оценить задержки, вносимые интеграцией с GitLab API.

*   **Команда запуска:**
    ```bash
    locust -f tests/load/locust_orchestrator.py --host http://localhost:8005
    ```
*   **Сценарий:**
    *   Получение списка задач (Issues) из GitLab.
    *   Проверка кэширования проектов.
    *   Сохранение результатов расчетов в Git-ветки.
*   **Ожидаемый Baseline:** Время ответа сильно зависит от скорости `git.utz.local`. Если p95 > 2 секунд, необходимо внедрение Redis для кэширования задач.

---

## 🛠 Общие параметры тестирования

Для получения сопоставимых данных используйте следующие настройки в Web-интерфейсе (`http://localhost:8089`):

1.  **Number of Users:** `50`
2.  **Spawn Rate:** `5` (пользователей в секунду)
3.  **Run Time:** Рекомендуется держать нагрузку не менее **5 минут** для стабилизации графиков.

## 📊 Как читать отчеты

После завершения теста нажмите **Download Data** -> **Download Report**. 

| Метрика | Что означает | Целевое значение |
| :--- | :--- | :--- |
| **RPS** | Кол-во запросов в секунду | Чем выше, тем лучше |
| **p95 (95%ile)** | 95% пользователей получили ответ быстрее этого времени | **< 800 ms** |
| **Failures** | Процент ошибок (400, 422, 500) | **0%** |

### Типичные ошибки при запуске:
*   **404 Not Found:** Неверный URL в скрипте. Сверьтесь со Swagger (`/docs`) соответствующего сервиса.
*   **422 Unprocessable Entity:** Ошибка валидации Pydantic. В скрипте Locust не хватает обязательного поля или неверный тип данных.
*   **500/502 Error:** Сервер упал. Проверьте логи командой `docker-compose logs --tail=20 backend`.
